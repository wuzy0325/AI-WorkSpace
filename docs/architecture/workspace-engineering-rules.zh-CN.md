# 工作空间工程规则总览

> 本文档是工作空间级的统一工程规则入口，整合前后端分离、后端分层、前端 UI 设计、编码规范与良好架构原则。
> 详细规则仍以根目录 `CLAUDE.md`、`docs/runbooks/code-standards.zh-CN.md`、`docs/runbooks/development-rules.md` 与项目级文档为准；本文用于统一理解、快速决策与落地执行。

## 1. 这份文档解决什么问题

当前工作空间已经存在多份规则文档，但内容分散在不同位置：

- 根目录 `CLAUDE.md`：架构总纲、六边形硬约束、代码放置决策树
- `docs/runbooks/development-rules.md`：开发规则、依赖边界、验证要求
- `docs/runbooks/code-standards.zh-CN.md`：编码、命名、注释、抽象规范
- `docs/architecture/*`：工作空间结构、模块设计、项目变体
- `projects/*/DESIGN.md`、`projects/*/README.md`、`projects/*/AGENTS.md`：项目级补充规则

工作空间**不是没有规则**，而是**缺一份把这些规则串起来的工作空间总览**。本文档就是这份总览。

## 2. 工作空间当前的总体架构

本工作空间采用：

- Go 后端
- Vue 3 前端
- Wails 桌面壳
- 六边形架构边界
- 多项目工作空间组织方式

典型结构如下：

```txt
projects/<project>/
├── apps/desktop-wails/
│   ├── frontend/          # Vue 3 UI
│   └── backend/           # Wails 绑定与桌面壳胶水层
├── services/api-go/
│   ├── cmd/
│   └── internal/
│       ├── core/
│       ├── usecase/
│       ├── ports/
│       └── adapters/
├── contracts/
├── tests/
└── deploy/
```

小型独立工具允许采用单模块变体，但仍必须保留以下逻辑边界：

- `core`
- `usecase`
- `ports`
- `adapters`
- `backend`
- `frontend`

一句话概括：

**前端负责显示与交互，后端负责业务与控制，六边形架构负责隔离变化。**

## 3. 前后端分离规则

这是整个工作空间最核心的规则之一。

### 3.1 前端负责什么

前端只负责：

- 展示
- 用户交互
- 页面状态
- 组件组合
- 图表与可视化
- 输入校验中的界面反馈

前端可以做：

- 弹窗开关
- 表单输入状态
- 列表筛选状态
- 图表展示状态
- 当前选中的设备卡片

前端不应做：

- 校准算法
- 数据采集控制核心逻辑
- 硬件协议编解码
- 设备状态机
- 文件系统直接操作
- 串口/TCP/UDP 直接访问

判断口诀：

**如果把 Vue UI 替换成 Web 页面、命令行或别的前端，这段逻辑仍然成立，那它应属于 Go 后端。**

### 3.2 后端负责什么

后端负责：

- 业务规则
- 领域模型
- 采集流程编排
- 校准算法
- 设备控制
- 配置持久化
- 报告生成
- 与硬件、存储、网络的交互

后端必须成为系统的“决策者”，前端只是“表达者”。

### 3.3 Wails 边界规则

`apps/desktop-wails/backend/` 是薄桥接层，只负责：

- 参数转换
- 调用 usecase
- 返回前端友好的结果

禁止：

- 在 Wails 绑定层写业务 if/else
- 在 Wails 绑定层直接访问硬件
- 在 Wails 绑定层直接写核心算法

Wails 是界面壳，不是业务层。

## 4. 后端架构规则

后端默认采用六边形架构，尤其适用于：

- 多设备类型
- 多协议通信
- 复杂校准流程
- 长期演进的采集平台

### 4.1 分层职责

`core/`

- 纯领域模型与业务规则
- 允许算法、规则、状态定义
- 不允许硬件、I/O、框架依赖

`usecase/`

- 负责编排多个领域对象与外部接口
- 调用 `ports`
- 不直接依赖具体硬件实现

`ports/`

- 只定义接口
- 不写实现
- 用来抽象设备、存储、扫描、推送等外部依赖

`adapters/`

- 具体实现 `ports`
- 包括硬件驱动、配置持久化、存储、扫描、报告生成等
- 不应承载领域规则

`api/` 或 Wails backend

- 处理协议边界
- 转换请求/响应
- 委派给 `usecase`

### 4.2 后端硬约束

以下规则是零容忍的：

- `core/` 禁止硬件导入、禁止文件 I/O、禁止网络、禁止框架依赖
- `ports/` 禁止实现逻辑
- `usecase/` 禁止直接调用硬件实现
- `adapters/hardware/` 禁止编写领域业务规则
- `apps/desktop-wails/backend/` 禁止承载核心业务逻辑

### 4.3 后端良好架构标准

一个好的后端架构应满足：

- 新增一种设备时，主要新增 adapter，而不是重写 core
- 更换持久化方式时，不需要修改 usecase
- 核心算法可以脱离真实硬件测试
- 设备仿真器能与真实设备共享同一组接口契约
- 入口层只做装配，不做业务决定

### 4.4 后端编码原则

- 业务名优先，避免缩写
- 函数短小，职责单一
- 参数校验在边界层完成
- 所有 I/O 操作显式处理错误
- 硬件通信必须具备超时、重试、恢复策略
- 长任务必须支持 context 取消
- 热路径减少不必要分配
- 资源必须显式释放

## 5. 前端与 UI 架构规则

前端的目标不是“页面能跑起来”，而是：

- 结构清楚
- 交互一致
- 样式统一
- 容易复用
- 不把业务逻辑错误地下沉到 UI

### 5.1 前端分层建议

推荐按以下逻辑分层：

- `app/`：应用启动、provider、layout、路由、全局 host
- `design/`：tokens、theme、motion、z-index、视觉基础设施
- `shared/ui/`：基础 UI 组件
- `shared/patterns/`：稳定复用的界面模式
- `features/`：业务功能模块
- `pages/`：页面级组装

### 5.2 UI 基础组件规则

基础 UI 组件应放在 `shared/ui/`，例如：

- `UiButton`
- `UiInput`
- `UiSelect`
- `UiDialog`
- `UiToggle`
- `UiPanel`

基础 UI 组件必须满足：

- 不依赖业务 store
- 不出现业务领域词
- 提供稳定 API
- 保持视觉一致
- 统一交互行为

### 5.3 Pattern 组件规则

Pattern 组件位于 `shared/patterns/`，解决重复出现的界面模式，例如：

- `FormField`
- `SettingsSection`
- `ConfirmActionDialog`
- `EmptyState`
- `LoadingState`

它们可以组合多个 `Ui*` 组件，但不应绑定设备、校准、采集等具体业务。

### 5.4 Feature 组件规则

业务组件必须放在 `features/*`，例如：

- `DeviceManagementDrawer`
- `GlobalSettingsModal`
- `TraversalWizard`
- `CalibrationSettingsPanel`

这些组件允许：

- 调用 store
- 调用业务 service
- 使用领域类型
- 处理业务流程

但不能反向污染 `shared/ui/`。

### 5.5 前端状态管理规则

本地状态适合放在组件内部：

- 弹窗开关
- hover
- tab
- 临时输入值

跨组件业务状态适合放在 store：

- 设备列表
- 当前采集状态
- 全局设置
- 工作流步骤状态

禁止：

- 通用 UI 组件直接依赖业务 store
- 为了省 props 把所有状态都塞进全局 store

### 5.6 UI 设计规则

工作空间的桌面 UI 以工业工具型界面为主，优先满足：

- 桌面优先
- 高信息密度
- 强状态可见性
- 低装饰噪音
- 动效克制

设计 token 应统一管理：

- 颜色
- 间距
- 字体
- 圆角
- 阴影
- 动效时长
- 层级

命名必须使用语义名，例如：

- `--color-bg-panel`
- `--color-text-primary`
- `--space-3`
- `--radius-md`
- `--z-dialog`

不要用：

- `blue1`
- `gray2`
- `gap13`
- `round2`

## 6. 编码规范

编码规范以 `docs/runbooks/code-standards.zh-CN.md` 为准，这里只提炼工作空间级共识。

### 6.1 命名规则

- 命名必须语义化
- 禁止拼音、无意义缩写、上下文不明简称
- 布尔值使用 `is`、`has`、`enable`、`allow` 等前缀

### 6.2 文件职责规则

- 一个文件只做一件事
- 一个函数只做一件事
- 超长文件应拆分
- 复杂流程拆为清晰子函数

### 6.3 注释规则

- 注释解释“为什么”，不解释“代码在做什么”
- 对外方法写文档注释
- 复杂业务规则写段落级说明
- 遗留问题统一使用 `TODO`、`FIXME`、`NOTE`

### 6.4 错误处理规则

- 不允许吞错误
- 所有外部依赖错误必须显式处理
- 参数校验尽量前置
- 边界层严格校验，内部调用少做重复校验

### 6.5 抽象与复用规则

- 复用优先于复制
- 相同逻辑在 2 个以上项目出现，应评估抽到 `shared/*`
- 相同逻辑重复 3 次以上，应抽函数或组件
- 抽象必须服务真实复用，不为“未来可能”过度设计

## 7. 良好架构的判断标准

无论前端还是后端，一个“好的架构”通常应该满足以下问题的答案大多为“是”：

### 7.1 边界清楚

- 能快速判断代码该放哪里
- 改前端不会误伤核心业务
- 换设备实现不需要改核心算法

### 7.2 可替换

- UI 可以替换但业务不丢
- 硬件适配器可以替换但 usecase 不重写
- 仿真器与真实设备共用接口契约

### 7.3 可测试

- core 不依赖真实硬件也能测
- usecase 可通过 fake/mock port 测
- 前端基础 UI 可单测
- 复杂流程可集成验证

### 7.4 可维护

- 新人能看懂目录
- 同类控件不需要反复造轮子
- 修改一个规则不会导致全局样式散乱
- 项目规模扩大后还能持续演进

## 8. 代码放置快速决策

遇到“这段代码该放哪”的问题时，可按下面判断：

### 8.1 后端相关

- 是纯业务规则或算法吗？放 `core/`
- 是编排多个对象与外部接口吗？放 `usecase/`
- 是外部依赖抽象吗？放 `ports/`
- 是具体设备、存储、扫描、文件实现吗？放 `adapters/`
- 是 API 或 Wails 入参出参转换吗？放 `api/` 或 `backend/`

### 8.2 前端相关

- 是通用控件吗？放 `shared/ui/`
- 是复用界面模式吗？放 `shared/patterns/`
- 是业务组件吗？放 `features/*`
- 是页面拼装吗？放 `pages/*`
- 是主题、颜色、间距、动效规则吗？放 `design/`

## 10. 落地建议

如果要让工作空间规则真正发挥作用，建议按以下顺序推进：

1. 先统一架构边界，不急着做目录美化
2. 先统一前后端职责，再谈 UI 组件库选型
3. 先设计 token 和交互规则，再扩展 UI 组件层
4. 先把新增代码放对，再逐步迁移旧代码
5. 复用出现两次就评估抽象，出现三次优先抽离

一句话总结：

**先立边界，再定规则；先定规则，再做结构；先把新代码写对，再逐步整理旧代码。**
