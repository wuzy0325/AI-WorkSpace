# AI 文档职责矩阵

> 目标：明确工作空间中每一份 AI 相关文档“该写什么、不该写什么、何时加载”，避免规则分散、重复、冲突，帮助 `OpenCode`、`Claude Code` 等 agent 稳定执行渐进式上下文加载。

## 1. 为什么需要职责矩阵

如果不定义文档职责，常见问题会很快出现：

- 同一条规则在多个文件重复出现
- `AGENTS.md` 越写越大，启动变重
- `CLAUDE.md` 同时承担总纲、项目例外、专题细节，边界模糊
- 项目 README 和 AGENTS 重复描述同一批命令与规则
- AI 无法判断哪个文件是入口，哪个文件是权威，哪个文件只是补充

职责矩阵的目标不是增加文档数量，而是：

- 降低启动上下文成本
- 明确权威来源
- 提高按需加载效率
- 减少规则漂移

## 2. 总体原则

文档职责遵循以下原则：

- 入口文档轻量化
- 总纲文档结构化
- 专题文档专业化
- 项目文档本地化
- 任务上下文即时化

一句话：

**入口只负责导航，规则由权威文档定义，任务只加载当前需要的那一层。**

## 3. 工作空间级职责矩阵

| 文档 | 主要职责 | 不应承载 | 何时加载 |
|---|---|---|---|
| `AGENTS.md` | 启动入口、最小边界、关键命令、文档导航、渐进加载协议入口 | 详细编码细则、项目级例外、长篇设计说明 | 每次启动时优先加载 |
| `CLAUDE.md` | 工作空间架构总纲、六边形边界、硬约束、代码放置决策树、设计原则 | 所有专题细则、所有项目例外、冗长 runbook | 架构判断、代码实现、重构前加载 |
| `docs/architecture/workspace-engineering-rules.zh-CN.md` | 整合版工程规则：前后端分离、后端规则、UI 规则、编码摘要、良好架构标准 | 逐行编码细则、项目特有实现细节 | 需要统一工程判断时加载 |
| `docs/architecture/ai-context-loading.zh-CN.md` | AI 渐进式上下文加载协议、任务加载顺序 | 业务规则、项目实现细节 | 设计或维护 AI 规则体系时加载 |
| `docs/architecture/ai-document-responsibility-matrix.zh-CN.md` | 文档职责边界、加载职责分工、反重复规范 | 具体业务或技术实现细节 | 调整规则体系、治理文档结构时加载 |
| `docs/runbooks/code-standards.zh-CN.md` | 编码、命名、注释、文件结构、抽象与复用细则 | 工作空间导航、项目级命令 | 进入编码细节时加载 |
| `docs/runbooks/development-rules.md` | 开发流程、依赖边界、验证要求、复用规则 | 项目业务规则、UI 视觉细节 | 实施任务与验证前加载 |
| `docs/architecture/module-design.md` | 模块设计细节、推荐模块结构 | 项目命令、通用编码细则 | 架构或模块划分任务时加载 |
| `docs/architecture/project-variants.md` | 项目结构变体、允许的项目布局 | 业务实现、编码细节 | 新项目/结构决策时加载 |
| `docs/index.md` | 文档导航索引 | 规则正文 | 查找文档入口时加载 |

## 4. 项目级职责矩阵

| 文档 | 主要职责 | 不应承载 | 何时加载 |
|---|---|---|---|
| `projects/<name>/AGENTS.md` | 项目级轻量入口、项目命令、项目边界、项目文档导航 | 项目长篇总说明、完整设计手册、重复 workspace 总规则 | 任务锁定到项目后优先加载 |
| `projects/<name>/README.md` | 项目概况、运行方式、目录说明、主要命令、开发入口 | 工作空间通用规则、细颗粒编码规范 | 初次进入项目时加载 |
| `projects/<name>/CLAUDE.md` | 项目架构特例、项目级硬约束、项目内部分层规则 | 所有 UI 设计细节、迁移实施步骤全文 | 架构实现或边界判断时加载 |
| `projects/<name>/DESIGN.md` | 项目 UI 设计原则、视觉目标、布局约束、风格边界 | 通用工程规则、后端分层规则 | 前端 UI / 设计任务时加载 |
| `projects/<name>/docs/migration/*.md` | 迁移背景、参考源、差异分析、迁移步骤 | 工作空间通用规则 | 涉及迁移任务时加载 |
| `projects/<name>/docs/runbooks/*.md` | 项目专项流程、运行模式、联调检查、HIL/集成验证 | 工作空间总纲 | 任务需要专项流程时加载 |

## 5. 任务级上下文职责

任务级上下文不应提前固化在入口文档中，而应在执行时即时加载。

包括：

- 当前将修改的源码文件
- 当前将修改的测试文件
- 当前报错日志
- 相似实现示例
- 当前 feature 的 spec / plan / ADR

任务级上下文的原则是：

- 靠近问题
- 只加载相关内容
- 用完就让出上下文预算

## 6. 入口文档写作规则

### 6.1 `AGENTS.md` 应该写什么

应该写：

- 这是一个什么工作空间/项目
- 最关键的边界和禁止事项
- 最关键的命令
- 该去哪里继续读
- 默认加载顺序

不应该写：

- 完整编码规范
- 全部项目例外
- 全部 UI token 细节
- 详细迁移步骤

### 6.2 `CLAUDE.md` 应该写什么

应该写：

- 架构总纲
- 分层边界
- 决策树
- 工作空间级硬约束
- 设计原则

不应该写：

- 每个项目的详细命令全集
- 过细的专题说明
- 运行中才会用到的大段操作 SOP

## 7. 权威性规则

为避免规则冲突，建议长期采用以下权威顺序：

1. 用户明确要求
2. 当前项目的强约束文档
3. 工作空间 `CLAUDE.md`
4. 工作空间专题规则文档
5. 项目 README / 辅助文档

如果同一规则必须在多个地方出现：

- 入口文档只保留摘要与链接
- 权威文档保留完整定义

## 8. 反模式清单

### 8.1 入口文档膨胀

表现：

- `AGENTS.md` 包含所有编码规则、所有项目说明、所有专题 runbook

后果：

- 启动上下文变重
- agent 难以聚焦

### 8.2 README 与 AGENTS 重复

表现：

- 命令、规则、目录说明在两个文件重复复制

后果：

- 更新时容易遗漏一份

### 8.3 项目文档反向覆盖工作空间规则但未声明

表现：

- 项目文档偷偷改变命名、分层或 UI 约束

后果：

- agent 无法判断是否例外

正确做法：

- 项目文档明确写“项目例外”或“项目补充”

## 9. 推荐维护方式

每次新增或修改 AI 规则文档时，都先回答这 4 个问题：

1. 这份文档是入口、总纲、专题、项目补充，还是任务材料？
2. 它的唯一职责是什么？
3. 哪些内容不该写进来？
4. AI 应该在什么时机加载它？

如果回答不清楚，说明这份文档的定位还不稳定。

## 10. 一句话版本

这套职责矩阵可以压缩成一句话：

**`AGENTS.md` 做入口，`CLAUDE.md` 做总纲，专题文档做细则，项目文档做本地补充，代码和错误输出做任务即时上下文。**
