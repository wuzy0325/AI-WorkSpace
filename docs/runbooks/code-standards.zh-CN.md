# 高质量代码结构规范

> 结构越规范、分层越清晰、约束越统一，AI 理解上下文、定位 Bug、重构、迭代新增功能的效率越高，且极少改崩代码、漏改逻辑。
> AI 不擅长理解混乱耦合、魔法变量、隐式逻辑、随意堆砌，极度依赖显性规则、固定结构、单一职责。

---

## 一、整体架构分层规范

### 严格单一职责分层

通用分层：**入口层 → 控制器/路由层 → 业务服务层 → 数据层 → 工具层**

- 禁止：路由里写 SQL、工具函数塞业务逻辑、一个文件混接口 + 业务 + 数据操作

### 架构模式选择

根据项目复杂度选择合适的分层模式：

#### 模式 A：标准三层架构（适用于 CRUD / 简单业务）

固定范式，AI 可快速定位文件：

```
src/
  api/         # 接口/路由/请求入参校验
  service/     # 核心业务逻辑
  model/       # 数据模型、结构体、枚举、常量
  dao/db/      # 数据库、缓存、外部资源操作
  utils/       # 纯工具：加密、格式化、通用计算
  config/      # 配置、环境变量、全局参数
  middleware/  # 中间件、拦截器、鉴权、日志
  types/       # 类型定义(TS/Rust)
```

#### 模式 B：六边形架构（适用于硬件 / 多领域 / 复杂业务）

当项目涉及多种外部系统（硬件、实时通信、多协议）、领域逻辑复杂时，标准三层架构的 `service/` + `dao/` 会导致：

- `service/` 既做编排又做实现，职责模糊
- `dao/` 无法涵盖硬件驱动、WebSocket、设备扫描等多种外部适配器
- 无接口抽象层，核心逻辑直接依赖具体实现，更换硬件需要改核心代码

推荐采用六边形架构（Ports & Adapters）：

```
services/<service>-rs/
├── Cargo.toml
└── src/
    ├── bin/                # 服务入口：依赖注入 + 启动
    ├── core/               # 纯业务领域模型 + 算法（≈ model/ 加强版）
    │   └── <domain>/       #   按领域拆分子模块：device/motion/calibration/...
    ├── ports/              # trait 抽象层（标准三层缺失的部分）
    │   ├── device.rs       #   定义 Device trait
    │   ├── motion.rs       #   定义 MotionController trait
    │   └── ...
    ├── usecase/            # 业务编排层（≈ service/ 加强版）
    │   ├── device_manager.rs
    │   ├── acquisition.rs
    │   └── ...
    └── adapters/           # 外部适配器（≈ dao/db/ 的泛化）
        ├── hardware/       #   硬件驱动：P1604、T1603、模拟
        ├── config/         #   配置持久化
        ├── ws/             #   WebSocket 实时推送
        ├── scan/           #   设备发现
        ├── storage/        #   文件存储
        ├── report/         #   报告生成
        ├── mq/             #   消息队列（预留）
        └── db/             #   数据库（预留）
```

**两种模式对照表：**

| 标准三层（模式 A） | 六边形架构（模式 B） | 说明 |
|------|------|------|
| `api/` | `src/bin` + API adapter | HTTP 路由/处理器保持薄层，职责不变 |
| — | `ports/` | **新增** — 接口抽象层，标准三层缺失，导致模块耦合 |
| `service/` | `usecase/` + `core/` | 拆为两层：纯领域逻辑（core）+ 编排（usecase） |
| `dao/db/` | `adapters/` | 从单一 DB 操作泛化为多种外部适配器 |
| `model/` | `core/<domain>/` | 从单一 model 拆为按领域组织的子包 |
| `utils/` | `pkg/` | 纯工具函数，职责不变 |
| `middleware/` | 在 `api/` 内 | 中间件，通常规模不大，放在 api 层内即可 |
| `types/` | 分散在 core + ports | Rust 类型定义靠近使用方，不单独成包 |
| — | `src/bin/` | **新增** — 显式入口 + 依赖注入 |

**何时选 A，何时选 B：**

| 特征 | 选 A | 选 B |
|------|------|------|
| 领域逻辑复杂度 | 简单 CRUD | 复杂算法/多领域 |
| 外部系统种类 | 仅 DB | 硬件 + 实时通信 + 文件 + 网络 |
| 是否需替换实现 | 否 | 是（需模拟设备、换硬件型号） |
| 团队规模 | 1-3 人 | 3+ 人或跨团队 |
| 生命周期 | 短期工具 | 长期演进产品 |

### 模块解耦

- 模块之间只依赖抽象/接口，不直接依赖内部实现
- 禁止跨模块全局变量硬引用

### 环境与配置隔离

- 所有密钥、地址、阈值、开关统一放配置文件
- 代码中无硬编码 IP、Token、魔法数字

## 二、文件 & 代码块结构规范

### 单文件职责唯一

一个文件只做一件事：一个路由、一个服务、一类工具。

### 文件长度限制

常规文件控制在 **300～500 行**内。超长文件强制拆分——AI 超长上下文极易理解错乱。

### 代码块顺序固定

推荐固定顺序，AI 阅读成本极低：

1. 包导入/依赖
2. 常量/枚举/全局配置
3. 类型/结构体定义
4. 中间件/钩子
5. 对外暴露方法/接口
6. 内部私有方法

### 函数/方法短小化

- 单个函数不超过 **50 行**
- 复杂逻辑拆分为子函数，拒绝巨型函数

## 三、命名规范

### 命名语义化

禁止缩写、拼音、乱简写：`userLoginCheck` ✅ / `usrChk` ❌

### 统一命名风格

| 场景 | 规范 |
|------|------|
| 前端 TS/JS | 小驼峰 `camelCase` |
| Rust/Python | 蛇形 `snake_case` |
| 类/结构体 | 大驼峰 `PascalCase` |

### 变量用途显性化

- 布尔值统一前缀：`is` / `has` / `enable` / `allow`
- 临时变量、缓存变量、返回变量命名区分开

### 禁止魔法值

所有 0、1、状态码、错误码、固定文案，全部定义为常量。

## 四、注释 & 文档规范

### 必须写模块级注释

每个文件顶部说明当前文件作用、依赖、业务场景。

### 所有对外方法必须写文档注释

标注：入参含义、出参结构、异常场景、使用限制。

### 复杂业务逻辑加段落注释

不是注释每一行，而是注释**为什么这么写、业务规则**。

### Bug 遗留/临时方案标记

统一标记：`// TODO:` / `// FIXME:` / `// NOTE:`

AI 可直接检索批量处理遗留问题。

## 五、逻辑与写法规范

### 拒绝深层嵌套

嵌套 `if`/`for` 不超过 **3 层**，多用提前 `return` 扁平化代码。

### 纯函数优先

通用工具方法：无副作用、不修改入参、依赖外部资源越少越好。

### 错误处理统一规范

- 全局统一错误码、统一返回格式
- 禁止吞异常、裸 `try/catch` 不处理

### 参数校验前置

所有接口入参、函数入参，第一行先校验。

### 避免隐式逻辑

不要靠全局变量、上下文隐式传参，尽量显式传参。

---

## 六、复用 & 抽象规范

### 重复代码必须抽离

重复出现 **3 次以上**逻辑，抽取为工具函数/公共方法。

### 通用能力抽象封装

缓存、OSS、短信、数据库、第三方请求统一封装 SDK。

### 业务规则集中管理

活动规则、权限规则、计算公式统一放在单独的 `rule` 模块。

---

## 七、AI 友好专属增强规则

### 固定编码风格 & 格式化

开启 ESLint / Prettier / `cargo fmt` 强制格式化，代码风格统一。

### 依赖版本固定

`package.json` / `Cargo.toml` / `Cargo.lock` / `requirements` 锁定版本，避免 AI 升级依赖炸库。

### 最小权限导出

只暴露必要方法，私有逻辑内部隐藏，防止 AI 乱调用内部函数。

### 关键流程可追踪

核心链路加日志、埋点，AI 排错时可快速还原执行流程。

### 避免奇葩语法 & 过度简写

少用三元嵌套、复杂链式调用、语法糖堆砌，保持写法朴素。

---

## 八、落地极简执行版

1. **选架构** — 简单 CRUD 用模式 A，硬件/多领域用模式 B（六边形）
2. **定目录** — 全项目统一目录结构，AI 不再猜位置
3. **限行数** — 单文件 ≤ 500 行，单函数 ≤ 50 行
4. **统一命名** — 语义化 + 常量替代魔法值
5. **分层解耦** — 禁止跨层乱写逻辑，依赖接口而非实现
6. **文档注释** — 对外方法必写，复杂逻辑写"为什么"
7. **错误统一** — 全局错误码 + 统一返回格式 + 参数校验前置
8. **格式化 + Lint** — 开启强制格式化，风格统一

---

## 为什么这套结构对 AI 特别有用？

| 原则 | 对 AI 的帮助 |
|------|-------------|
| 结构固定 | AI 不用猜测代码位置，改 Bug、加功能精准定位 |
| 拆分细致 | AI 单次只需要理解小片段，不会上下文过载 |
| 语义命名 + 注释 | AI 读懂业务意图，不只读懂代码语法 |
| 解耦分层 | AI 修改某一块逻辑，不会误伤其他模块 |
