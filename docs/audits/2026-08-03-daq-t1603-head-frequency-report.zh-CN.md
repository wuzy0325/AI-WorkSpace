# DAQ-T-1603 HEAD 帧序号与高频采样实测报告

## 1. 目的

验证 DAQ-T-1603（192.168.1.10:9000，FW 1.04）在开启 HEAD（帧序号）后的帧格式，
并评估 500Hz / 1000Hz 高频采样下的数据质量。本报告记录 2026-08-03 实机验证结论，
为驱动默认开启 HEAD 提供依据。

## 2. 测试环境

| 项目 | 实际值 |
|------|--------|
| 测试日期 | 2026-08-03 |
| 设备地址 | `192.168.1.10:9000` |
| 本机地址 | `192.168.1.11` |
| 固件版本 | FW 1.04（型号 `T1603`） |
| 通道 | 仅 CH02 接入热电偶（~26-30℃），其余通道 0 |
| 测试程序 | Go 驱动 `shared/device-sdk/go` + 原始 TCP 探针 |

## 3. 关键发现：SPS 参数是采样间隔，不是频率

固件 `@fe SPS <n>` 参数语义为**采样间隔**（单位 1/1000s），实际频率 = `1000/SPS` Hz：

| SPS | 实际频率 | 实测帧率（30s） |
|-----|---------|-----------------|
| 1 | 1000Hz | ~29678 帧 |
| 2 | 500Hz | ~14940 帧 |
| 3 | 333Hz | ~9950 帧 |
| 5 | 200Hz | ~5969 帧 |
| 500 | 2Hz | ~60 帧 |

**坑**：小数 SPS 会被设备截断为整数（`@fe SPS 2.5` 读回 `2`），因此 400Hz / 480Hz
无法精确设置（需要 SPS=2.5 / 2.08），可选频率是 `1000/整数` 的离散集合。

## 4. HEAD=1 帧格式（实机确认）

开启 HEAD（`@fe HEAD 1`）后，二进制帧携带 4 字节帧序号头：

| HEAD | TIME | 帧格式 | 帧长 |
|------|------|--------|------|
| 0 | 0 | `[64 数据]` | 64 |
| 0 | 1 | `[sec][ns][64 数据]` | 72 |
| **1** | **0** | **`[seq][64 数据]`** | **68** |
| 1 | 1 | `[seq][sec][ns][64 数据]` | 76 |

- 序号 `seq` 为 uint32 LE，**每帧 +1 连续**，可从 0 开始
- 时间戳 `sec`/`ns` 为 uint32 LE（秒 + 纳秒）
- 通道顺序仍为 CH15→CH0（解析后需 reverse）
- 帧序号可用于**丢帧/错帧检测**：序号断档即说明数据不连续

## 5. 数据质量：各频率实测

### 5.1 500Hz（SPS=2）

HEAD=1 开启，60s 采集 29877 帧：

- **帧序号完全连续**（0,1,2,...），无丢帧、无错帧、无边界漂移
- CH02 数据**偶发跳变**：多次独立采集表现不同（0 次 ~ 500+ 次跳变 >2℃），
  异常值常见 **64-65℃**（固定值，与 1000Hz 溢出值同源），呈"正常值↔异常值"交替
- 结论：帧层面无问题；跳变是**设备 ADC 真实数据异常**（间歇性），非解析问题

### 5.2 1000Hz（SPS=1）

HEAD=1 开启，30s 采集 29678 帧：

- 帧序号**完全连续**，无丢帧
- 但 CH02 **528 次跳变**，异常值固定为 **64.59℃**，且呈规律性：
  `26.5 → 64.59 → 26.5 → 64.59`（**每隔 1 帧出现一次**）
- 结论：1000Hz 下设备每 2 帧就有 1 帧输出溢出错值，**1000Hz 不可用**

### 5.3 333Hz 及以下

| 频率 | 帧序号 | CH02 跳变 |
|------|--------|-----------|
| 333Hz | 连续 | 0 |
| 200Hz | 连续 | 0 |
| 100Hz | 连续 | 0 |
| 50/20/10/5/2Hz | 连续 | 0 |

333Hz 及以下完全干净。

## 6. 关于"开 HEAD 后不跳变"的澄清

早期观察曾怀疑"开 HEAD 后 500Hz 不跳变"。A/B 对照与多轮复测表明：

- 500Hz 的 CH02 跳变是**间歇性**的，与 HEAD 开关无关
- 开 HEAD 的价值在于：**用帧序号连续性排除"解析错位"这一嫌疑**，从而
  确认跳变是设备数据本身的异常，而非软件解析问题
- 结论：HEAD 不改变数据内容，只是提供帧完整性校验手段

## 7. @f0 ACK 是否穿插进数据流（实机验证）

用帧序号连续性定位流中额外字节（`detectLateAck` 检测器）：

| 频率 | 时长 | ACK 穿插 | 序号断档 |
|------|------|---------|---------|
| 500Hz | 60s | **0** | 0 |
| 333Hz | 60s | **0** | 0 |

开启 HEAD=1 后，60 秒内**未观察到** `A` ACK 晚到穿插进数据帧流的情况
（此前 HEAD=0 时代记录过该现象）。HEAD=1 的 4 字节序号头使帧边界自带校验，
即使有穿插也能被序号连续性立即发现。

## 8. 生产代码变更（2026-08-03）

1. **驱动默认开启 HEAD**：`syncHardwareConfigLocked` 将 `@fe HEAD 0` 改为
   `@fe HEAD 1`，并读回 `@fd HEAD` 验证生效
2. **帧解析支持序号帧**：
   - `TCPFrameSizeWithSequence = 68` / `TCPFrameSizeWithSequenceAndTimestamp = 76`
   - `ParseTCPFrameEx` 新增 68/76 字节分支
   - `T1603FrameReader` 新增 `SetSequenceMode`，`frameSizeLocked` 按
     sequence/metadata/binary 组合返回 64/68/72/76
3. **数据面透传序号**：`core.DataPayload` 新增 `SequenceNumber` 字段，
   `processPayload` 填充

## 9. 使用建议

1. **推荐工作频率**：500Hz（SPS=2）或 333Hz（SPS=3）
2. **1000Hz 不可用**：数据半数溢出错值（64.59℃）
3. **建议开启 HEAD**：用帧序号连续性做数据完整性校验，
   序号断档即判定该段时间数据不可信
4. 若 500Hz 的偶发 64-65℃ 尖峰不可接受，降频到 333Hz 可完全消除
