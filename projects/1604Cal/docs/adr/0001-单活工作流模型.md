# 单活工作流模型

后端采用"系统同一时刻只允许一个业务流程拥有设备操作上下文"的模型，而不是多模块共享或抢占模型。

## 状态

accepted

## 背景

设备会话绑定原来是全局单例配一个 `moduleName` 字符串做冲突判断。`calibration`、`measurement` 两个服务共享同一个 `session.Service`，`apiServer` 上还存了全局 `sessionToken`。谁最后调用绑定，设备操作上下文就归谁，没有认领/释放协议。

这意味着：运行中的计量采集可能被标定页面的一次绑定覆盖；后台 goroutine 可能继续操作已经不属于它的设备。

## 决策

采用单活工作流模型：

- 系统同一时刻只有一个**活跃工作流**拥有**设备操作上下文**
- 新工作流试图绑定设备时，后端必须拒绝（`409 WORKFLOW_CONFLICT`），永不自动抢占
- 引入后端 `WorkflowCoordinator`，统一负责冲突判定、状态迁移、安全释放和人工处理
- `BindingToken` 不再是 API 层全局字段，降级为内部操作上下文 id，供后台 goroutine 校验
- 应用服务不再直接调用裸 `SessionMachine.Transition()`，通过 coordinator 暴露业务动作

### 活跃工作流判定

`ready`、`paused`、`pressurizing`、`stabilizing`、`collecting`、`await_alarm_resolution`、`await_manual_collect`、`point_done`、`fitting` 为活跃；`idle`、`stopped`、`completed`、`error` 为非活跃。

### 错误处理

安全释放失败时进入 `requires_manual_intervention`，阻止新流程，要求操作者检查硬件后确认。

### 维护操作

设备管理与多打压控制在活跃工作流期间禁止写所有设备，允许读所有设备；紧急停止始终允许，但驱动进入人工处理。

## 考虑过的替代方案

1. **多租约 token**：每个模块持有独立 `BindingToken`，并发操作不同设备。放弃原因是 WTS 系统单组设备同一时刻只需要一个业务流程，且真实硬件无法被两个流程安全共享。
2. **自动抢占**：新绑定自动停止旧流程。放弃原因是设备操作涉及真实打压、阀门和采集，自动抢占可能留下不安全硬件状态。
3. **前端独占**：只在 UI 层禁用按钮。放弃原因是后端 goroutine、SSE 事件、多窗口仍然可能误操作设备。
