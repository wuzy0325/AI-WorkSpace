# 阀门=校准模式 作为标定与计量启动的必要条件

后端把"阀门处于校准模式"作为**标定 + 计量**两条启动路径的**共同**门禁前置条件，由 `calibration.enforceValveCalibrationGate` 开关统一控制，默认开启。

## 状态

accepted

## 背景

WTN1604 1604 计量设备的气路结构决定了：
- **校准模式**（阀门 = `w0C01` / 读阀返回 `A1`）：气路与外部压力源连通，可以做标定数据采集，也可以接收稳定压力做计量。
- **测量模式**（阀门 = `w0C00` / 读阀返回 `A2`/`A3`）：气路转入内部参考腔，外部压力源被隔离，此时无论做标定还是做计量都拿不到可用数据。

历史问题：
1. 标定模块原本有阀门门禁的钩子，但前端硬编码 `enforceValveCalibrationGate=false`、后端默认值也是 `false`，门禁能力实际**没有生效**。
2. 计量模块完全没有阀门门禁，可以在测量模式下点"开始采集"，最终会得到一组无意义的零压数据，再由用户自己肉眼判断异常——这种"静默失败"在现场很难定位。
3. 推阀按钮点击后，因为 `0` 被武断当成 measurement、`N09` 之类的设备拒绝错误被吞掉，用户经常只能看到"按钮按了没反应"。

需要把"阀门=校准"这个**物理必要条件**显式化为代码层的**启动门禁**，并对一次推阀失败给出明确的可读反馈。

## 决策

**1. 门禁条件统一**

`阀门 = ValveStateCalibration`（domain.ValveState 常量，对应固件响应 `A1`）是以下两条启动路径的**共同**必要条件：
- `POST /api/v1/sessions/start`（标定）
- `POST /api/v1/measurement/start`（计量自动 / 手动）

任一条路径在状态迁移与 `coordinator.Begin` 之前，先做一次**锁外**的 `ReadValveStatus(ctx)`：
- 读阀失败 → wrap `apperrors.ErrPrerequisiteNotMet` 抛出 → HTTP 409 `PREREQUISITE_NOT_MET`
- 读阀成功但 `valveStatus != calibration` → 同样 wrap `ErrPrerequisiteNotMet` 抛出
- 校准态 → 继续后续启动流程

**2. 开关同源**

整个应用只有一个开关：`calibration.enforceValveCalibrationGate`。
- 文件配置 `configs/app.json` → `config.AppConfig.Calibration.EnforceValveCalibrationGate`
- HTTP 装配层 `assembly.go` 把这个值**同时**注入 `calibration.Service` 与 `measurement.Service` 的 `StartPrerequisiteConfig`
- 前端通过 `GET /api/v1/config/gates` 拉取后存入 `useGatesStore`，calibration 与 measurement 两个 store 都从 gate store 取 computed 值

**默认值 = `true`**（严格门禁）。联调或现场调试需要绕过时，运维统一改后端配置文件即可，无需重新发布前端。

**3. 阀门状态语义化**

阀门状态在 `internal/domain/valve.go` 定义为 `ValveState` 三态枚举：
- `ValveStateCalibration` = `"calibration"`
- `ValveStateMeasurement` = `"measurement"`
- `ValveStateUnknown` = `"unknown"`

驱动层 `infrastructure/driver` re-export 同名字符串常量，应用层与协议层共用，避免到处硬编码 `"calibration"` 字面量。

固件读阀响应 `0` **不再武断归类为 measurement**，而是 `unknown`，让门禁严格拒绝，由 UI 提示"阀门状态未知，请确认设备"。

**4. 推阀反馈四态化**

`SetValveStatus` 把 `Nxx` 拒绝码识别为 `device rejected valve command <cmd>: <Nxx>` 错误，前端在 `useValveControl` composable 中区分四种用户反馈：
- 成功：弹 success "阀门已切换到 X 模式"
- 设备拒绝（含 N09）：弹 error，文案包含原始拒绝码
- 命令应答 A 但回读不一致：弹 warning "阀门当前仍为 X 模式，请检查设备"
- 回读 unknown：弹 warning "已下发指令，但阀门状态未知，请确认设备"

写后回读在前端做（300ms 延时 + `refreshValveStatus`），后端 `PUT /api/v1/session/valve` 不再二次同步读阀，避免 3s+3s 累计延迟。

## 备选方案

### 备选 A：把开关默认值改成 `false` 由 UI 警告替代后端拦截
- 优点：不阻断"现场设备阀门读数异常但物理上其实可用"的偶发场景
- 缺点：违反"硬件物理约束应成为代码硬约束"原则；静默失败成本远大于偶发拦截误报；UI 警告极易被忽略
- 拒绝原因：物理约束必须由后端权威拦截，前端 UI 只是辅助提示

### 备选 B：把开关拆成 `enforceValveCalibrationGateForCalibration` 与 `enforceValveCalibrationGateForMeasurement` 两个独立开关
- 优点：两条路径可以独立配置
- 缺点：违反实际物理含义（两条路径有完全相同的物理前置条件）；增加配置心智负担；增加状态空间（true/true、true/false、false/true、false/false 4 种组合中只有 2 种有现实意义）
- 拒绝原因：YAGNI；如果未来真要分裂，可以在升格为 `WorkflowGateConfig` 时再拆

### 备选 C：把读阀放在 `coordinator.Begin` 之后
- 优点：实现更简单（一次性放到事务里）
- 缺点：读阀失败需要立即回滚 coordinator；TCP 读阀最长 3 秒，会拖住会话锁；多路并发请求互相阻塞
- 拒绝原因：当前实现把读阀放在锁外、Begin 之前；calibration 路径如果在 Begin 之后失败，需要显式 `coordinator.End()` 回滚（已在 `StartCalibration` 中实现）

## 后果

**好处**

- 物理不可能成功的启动路径在代码层就被拒绝，避免"静默失败 + 用户排查 30 分钟"
- 开关同源后，运维一处改动即可对前后端同时生效，不会出现"前端硬拦但后端放过"或反向不一致
- 用户首次接触一台陌生设备时，从"按钮没反应"升级到"看到具体的设备拒绝原因"，故障定位时间显著下降
- 后续如果引入新的工作流模块（如多压源同步），可以复用同一份阀门门禁与 gate store

**代价 / 风险**

- 每次启动多了 1 次最长 3 秒的 TCP 读阀，对网络抖动敏感。已通过锁外读取 + ctx 超时缓解；后续可加入 store 层短期缓存（valveStatus 30s 内有效）
- 联调场景需要显式改后端配置才能绕过，需在内部 onboarding 文档中明确"如何关闭门禁"
- `enforceValveCalibrationGate` 这个配置项的命名仍以 calibration 起头但实际管控 measurement，命名约束放在了"配置兼容性"一侧；下一次大版本重构可考虑升格为 `WorkflowGateConfig`（参考 [internal/config/app_config.go](../../internal/config/app_config.go)）
